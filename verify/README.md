## 缺文件了？那是故意的

以下三个文件**不在仓库里**，因为它们是 Alice 的真实微信聊天记录：

- `groundtruth.json` — 微信数据库导出的标准答案（44 条消息）
- `expected_output.md` — 算法还原出的结果，字符级 93.7%
- 测试用的 `.mp4` 录屏

（跑基准产生的长图在 `verify/out/`，同样被忽略。）

它们在本地存在（Alice 的机器上），验收时直接用。**不要想办法把它们弄进仓库**，这个仓将来可能公开。

跑基准产生的长图落在 `verify/out/`，该目录整个被 gitignore。

> ⚠️ **2026-08-28 出过一次事故，记在这里当教训**：`.gitignore` 原本按文件名写死
> `verify/long_node.jpg`，后来把编码从 JPEG 改成 BMP，改了代码、改了文档，
> **没改这条规则**，于是 25.9MB 的真实微信聊天长图进了三个 commit，
> 由 Codex 冷读时发现（当时仓库还没有 remote，才来得及改写历史清掉）。
> 现在是双保险：按**类型**拦（`*.bmp` `*.png` `*.jpg` `*.mp4`…）+ 产物落独立忽略目录。
> **按文件名写的忽略规则会在实现变化时静默失效**，别再这么写。

## 怎么跑基准

```bash
cd verify && npm install
# 先用 ffmpeg 把测试录屏抽成帧目录
ffmpeg -v error -i <录屏.mp4> -vf fps=4 -q:v 2 /tmp/frames/f_%04d.jpg
node run-node.js /tmp/frames 4 wechat
```

期望输出：

```
[wechat] 预扫 12 帧 → 滚动区 y154~1522 (高 1368)
108 帧 → 关键帧 6 张，丢弃回弹帧 3
长图 720x5106 → out/long_node.bmp (10.5 MB)
耗时 ms: {"预扫":~350,"取帧与位移":~3100,"拼接":~85,"BMP编码":~40,"总耗时":~3600}
细分 ms: {"shiftThumbMs":0,"decodeMs":~2550,"grayMs":~25,"shiftMs":~400,"keyframeMs":~150,"pauseMs":0}
```

长图高度差 5px 以内算通过。

Node 已经拿到 ffmpeg 抽好的 JPEG，因此 `shiftThumbMs` 和 `pauseMs` 固定为 0；
真机 App 会显示原 7 项加这 6 项，共 13 行。位移阶段若出现超过
`max(100ms, frameShift×1%)` 的对账差额，耗时面板会显式告警；正差额表示仍有未分类开销，
负差额表示计时范围可能重叠。耗时会随机器波动，基准验收只看长图尺寸。

## 怎么算准确率

```bash
python3 score.py <你的输出.md> groundtruth.json <标签>
```

**唯一的准确率标准是 `groundtruth.json`**（微信数据库导出的真实记录）。
`expected_output.md` 只是"我这边跑出来的参考输出"，它自己就带 6% 误差，
**不要拿它当标准答案去比** —— 那样测的是"像不像我的输出"，不是"还原得对不对"。

同时给三个数：逐条准确率、字符级准确率、发言人准确率。

**看字符级那个。** 逐条准确率在 41 条的分母下一条就是 2.4 个百分点，实测在 87.8%–92.7% 之间抖；字符级稳定在 93.7%–94.0%，只抖 0.3 个点。要对外报数字就报字符级。
